# Refund budget ledger

Migration `0005_refund_budget.sql` installs the budget schema and uses the existing `audit_identity_change()` trigger function. Grant only `EXECUTE` on `reserve_refund_budget(uuid,uuid,uuid,uuid,text)` and `finalize_refund_budget(uuid,uuid,uuid,text)` to `apl_worker`; grant neither direct ledger table mutation nor ledger functions to API or public. As with the other security definer functions, retain a separately controlled migration owner and transaction-local tenant/environment context. Run the runtime under a restricted non-owner role. Config publication is operator-controlled.

Configure the mandatory connection row with daily and outstanding USD minor-unit limits. Optional workload limits use the canonical workload UUID string; optional customer limits use a provider-verified reference scoped to the connection. `None` is only for a verified resource with no applicable customer association; missing or uncertain provider facts are a caller error when customer budgets can apply. Request metadata must never supply a customer scope. New optional limits include existing matching daily and held usage, even if a limit was configured after dispatch. Lowering a limit blocks new holds without rewriting usage. Zero limits explicitly block admission.

Call `reserve()` within the `READ COMMITTED` dispatch transaction, after setting `apl.tenant_id` and `apl.environment_id` locally and locking action, authorization/control rows, and policy per the application order. The ledger then locks the connection's budget row; all operations and optional configuration writes share this mutex. Reserve/settle one logical action at a time per transaction, or apply a common batch lock order; administrative transactions that change multiple budget connections must likewise order by tenant/environment/connection. A missing mandatory connection config fails closed. Every applicable capacity check happens before writing anything, and sums use PostgreSQL numeric to avoid bigint overflow.

Commit a new hold with immutable dispatch authorization and stable provider idempotency key before making an external call. `AlreadyHeld` does not imply a provider call is safe to repeat; retries require separate fencing, reconciliation, and provider idempotency checks. `Settled`/`Released` are terminal, never permission to send a new request. Record confirmed evidence, apply `finalize()`, and change action status in the same transaction. A repeated matching finalization is idempotent; an opposite result is a conflict. Pending/unknown outcomes leave the hold alone. Never interpret an expired lease or a transport error as confirmed non-execution.

The dispatch date uses the PostgreSQL clock in UTC after acquiring the connection lock. Current-day holds and settlements consume that day's limit, and every open hold consumes outstanding capacity across all days. Late settlement stays attributed to the original day. Reservation amounts/scopes are immutable, terminal state changes once, and the append-only event table captures the limits applied at admission. Usage is derived directly from the action reservations, so cached totals cannot drift.

On a dedicated PostgreSQL test database, run `TEST_DATABASE_URL=… cargo test -p apl-ledger --test postgres -- --ignored`. This applies migrations and runtime roles, runs the ledger SQL contract, and tests concurrent admission through the Rust interface.
