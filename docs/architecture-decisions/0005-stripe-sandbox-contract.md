# ADR 0005: Stripe sandbox refund contract

Status: adapter, trusted routing, and opt-in sandbox worker implemented; verified with loopback mock HTTP and PostgreSQL fixtures. No Stripe account or API key has been connected.

Start with direct captured, paid USD card Charges in sandbox mode. Resolve an exact `ch_` resource under a trusted connection, inspect its captured and previously refunded amounts, and derive the customer scope from Stripe's response. Reject live-mode, disputed, unsupported, or insufficiently refundable Charges before authorization. Keep provider account, connection, and credentials in server configuration; request data cannot select an account or API host. Never use a customer reference supplied in action metadata. [Charge object](https://docs.stripe.com/api/charges/object)

Submit the exact verified charge and minor-unit amount, with the persisted idempotency key and a reserved correlation metadata field. Use the same provider account for reconciliation. Validate response correlation, charge, amount, currency, and sandbox mode before accepting an outcome. A successful response needs provider evidence; pending, requires-action, malformed, and ambiguous transport responses retain the budget hold. [Create refund](https://docs.stripe.com/api/refunds/create) · [Refund object](https://docs.stripe.com/api/refunds/object)

Reconciliation can list refunds for the exact charge and match the reserved correlation value, using bounded pagination. An absent result, list failure, or ambiguous match is unknown. A release requires authenticated terminal evidence for the exact operation, never mere absence. The default connector mode reconciles without automatic replays; supporting replay later requires an explicit account-specific safety window and fault tests. Stripe can prune idempotency keys, so a repeated key is not a permanent duplicate prevention mechanism. [List refunds](https://docs.stripe.com/api/refunds/list) · [Idempotent requests](https://docs.stripe.com/api/idempotent_requests)

Migration 0007 binds each provider namespace to one connection. The fake picker excludes routed jobs, and dispatch rechecks the binding after locking connection authorization. A short transaction lock and a unique open-dispatch index serialize requests for the same namespace/payment. The next request does not reserve funds while the payment is held, including manual review. If an earlier request settled or released after the next request's Charge read began, the next request must reverify before authorization.
